## Final follow-up (2026-10-26)

**The two original findings are closed in the reviewed implementation.** Reconciliation now compares the actual persisted scheduler's name, cron, timezone, repeat bounds, full template data, and options with the database-derived definition (`server/src/modules/job/job-scheduler.service.ts:180-207`). An unchanged scheduler is left in place even when its digest is missing or stale; only the digest is repaired (`:202-205`). An actually drifted scheduler is upserted even if the digest already matches (`:208-223`). The shared lease and database read under that lease remain in place (`:119-165`). Thus the stale-nonempty-digest state that remained after the first fix no longer deletes an overdue occurrence.

I reran the same isolated-Redis scenario against the actual `JobSchedulerService` with a random `nova-review-final-<uuid>:` prefix. Before reconciliation, `repeat:definition-7001:1793001066000` was overdue and `delayed`, with a deliberately stale nonempty digest. After reconciliation, that exact job was still `delayed`, the scheduler's next ID was unchanged, and the digest was repaired to its original value. Cleanup touched only that random prefix.

The persisted-`ats` activation budget remains in place (`server/src/modules/job/job-scheduler.service.ts:286-336`), with its claim-time increment confirmed in the installed BullMQ source as described below. My narrow Redis rerun selected the missing-digest, stale-digest, template-drift, repeat-option-drift, and activation-budget cases: **5/5 passed** (`JOB_QUEUE_REDIS_TEST=true pnpm --dir server exec jest --config test/jest-unit.json --runInBand --watchman=false --testMatch '**/job/job-runtime.integration-spec.ts' -t 'unchanged reconciliation preserves|repairs actual scheduler|terminates a scheduled occurrence'`). The other seven cases were skipped in this rerun; the parent is running the complete suite. I found no remaining P1/P2 issue in this focused review. Implementation files were not changed.

### Stalled-recovery timing addendum

The later worker setting keeps the 30-second renewable lock and scans for stalled jobs every 10 seconds (`server/src/modules/job/job-queue.ts:5-9,64-71`). In installed BullMQ, a shared `stalled-check` gate can reject a scan, and an admitted scan first marks active jobs; a later admitted scan with no lock requeues them (`node_modules/.pnpm/bullmq@5.81.5/node_modules/bullmq/dist/cjs/scripts/moveStalledJobsToWait-9.js:123-187`). The fast real-Redis protocol test checks denied → mark → reclaim, the blocked global lane, and the claim count advancing from 1 to 2 (`server/test/job/job-runtime.integration-spec.ts:437-504`). I reran only this protocol test: **1/1 passed**. The operations note and foundation report correctly distinguish the local test's 65-second budget from a production recovery guarantee (`docs/operations/job-worker.md:30`; `docs/quality/reports/2026-10-26-job-queue-foundation.md:72-88`). I did not rerun the roughly 40-second SIGKILL test while the parent ran the complete suite.

One coverage limit remains: the SIGKILL test seeds a gate with `stalledInterval + 500 ms` **before** starting the recovery worker (`server/test/job/job-runtime.integration-spec.ts:549-559`). If startup takes more than 500 ms, the first timed scan need not be denied; the test does not assert that specific scan was denied. The separate protocol test deterministically covers that state transition, so this is a limit on the end-to-end test's claimed adverse phase, not a newly observed production recovery defect. I found no material P1/P2 issue in this increment.

## Intermediate follow-up (historical, before the final fix)

**P1 remains open for a partial-update state.** The lease serializes normal reconcilers, and the new digest check avoids upserting an unchanged definition (`server/src/modules/job/job-scheduler.service.ts:118-181`). The no-digest adoption branch also preserves an existing unchanged scheduler (`:182-194`); its focused Redis test passes (`server/test/job/job-runtime.integration-spec.ts:161-191`). However, a changed definition is upserted first (`:197-213`) and its new digest is written in a separate Redis command (`:214-215`). If the process exits, the lease is lost, or that digest write fails between those commands, Redis retains the **old nonempty digest** with the **new scheduler**. The next reconciliation sees `previousDigest !== digest`, cannot enter the `!previousDigest` adoption branch, and upserts the already-current scheduler again. BullMQ then removes its overdue next occurrence, reproducing the original silent loss.

I reproduced this reachable intermediate state with the actual `JobSchedulerService` against isolated Redis 16389, using a random `nova-review-followup-<uuid>:` prefix. After installing a scheduler, I retained its existing next job and set its digest to a stale nonempty value, equivalent to an interrupted definition update after upsert. Once `repeat:definition-7001:1793000522000` was overdue and still `delayed`, `schedule()` removed that job and advanced the scheduler to `repeat:definition-7001:1793000523000`. The reproduction cleaned its own Redis keys. The new test clears the digest entirely; it does not cover this stale-but-present state. This is a remaining **P1** durability defect, although the normal unchanged-definition path is fixed.

**P2 is closed for the reviewed BullMQ version.** `moveToActive` atomically increments persisted `ats` before returning the claimed job (`node_modules/.pnpm/bullmq@5.81.5/node_modules/bullmq/dist/cjs/scripts/moveToActive-11.js:128-145`), and `Job.fromJSON` exposes that value as `attemptsStarted` (`node_modules/.pnpm/bullmq@5.81.5/node_modules/bullmq/dist/cjs/classes/job.js:198-216`). The processor rejects activation 4 before invoking the handler with `UnrecoverableError` and records a terminal failure (`server/src/modules/job/job-scheduler.service.ts:278-328`). This bounds scheduled poison jobs despite BullMQ's repeatable-job exemption from `maxStalledCount`. The focused Redis test uses a real scheduler job, seeds three earlier activations, and verifies the next claim fails without handler invocation (`server/test/job/job-runtime.integration-spec.ts:193-210`). It is a protocol-level test, not a repeated-SIGKILL test.

Independent narrow rerun: `JOB_QUEUE_REDIS_TEST=true pnpm --dir server exec jest --config test/jest-unit.json --runInBand --watchman=false --testMatch '**/job/job-runtime.integration-spec.ts' -t 'unchanged reconciliation preserves|terminates a scheduled occurrence'` passed **2/2**; the other seven integration cases were skipped. No implementation files were changed in this follow-up.

## Initial findings (historical)

The source line ranges in this section describe the initial version; use the follow-up section above for current line locations and finding status.

### P1 — Periodic reconciliation can delete an occurrence that is already due

`JobSchedulerService` calls `reconcile()` every 15 seconds (`server/src/modules/job/job-scheduler.service.ts:61-63`). `syncSchedules()` then unconditionally calls `upsertJobScheduler()` for **every** active definition (`:118-141`), even when its cron, handler, and timezone have not changed. With the global execution lane occupied (`:42-44`), the next scheduled occurrence can be in BullMQ's delayed set after its due time. BullMQ 5.81.5's upsert Lua removes the existing delayed/waiting occurrence, calculates the next cron time from **now**, and inserts a replacement (`node_modules/.pnpm/bullmq@5.81.5/node_modules/bullmq/dist/cjs/scripts/addJobScheduler-11.js:481-551,591-597`). This drops an occurrence that was already durably enqueued, without running it or writing a job log. Any CRUD call that invokes `schedule()` also reconciles all definitions (`server/src/modules/job/job-scheduler.service.ts:79-82`), so it can cause the same loss.

Targeted isolated Redis reproduction on port 16389, random `nova-review-<uuid>` prefix: schedule a one-second cron, hold its first handler while the next occurrence becomes overdue, then call the identical `upsertJobScheduler()`. Immediately before upsert, `repeat:definition-1:1792999468000` existed in `delayed` with due time 1792999468000 and current time 1792999469203. Immediately after upsert, that job no longer existed and the scheduler's next ID was `repeat:definition-1:1792999470000`. The reproduction cleaned its own queue and did not use a database. This contradicts the durable-trigger behavior promised by `docs/operations/job-worker.md:16-25` and the Task 3 plan's persistent-queue requirement.

### P2 — The configured stalled limit does not bound scheduled occurrence recovery

The worker sets `maxStalledCount: 1` (`server/src/modules/job/job-queue.ts:60-66`), and the operations note says this permits one stalled recovery (`docs/operations/job-worker.md:32`). Scheduled jobs are created by `upsertJobScheduler()` (`server/src/modules/job/job-scheduler.service.ts:125-141`), which gives them BullMQ's repeatable-job marker. In the installed BullMQ 5.81.5 stalled-job Lua, a job exceeding the limit is marked failed only when it is **not** a repeatable job (`node_modules/.pnpm/bullmq@5.81.5/node_modules/bullmq/dist/cjs/scripts/moveStalledJobsToWait-9.js:147-174`). A scheduled occurrence whose handler repeatedly kills its process can therefore be moved back to waiting without a terminal failure, regardless of `maxStalledCount`. The seven reported integration tests kill a process while processing a **manual** job (`server/test/job/job-runtime.integration-spec.ts:282-324`), so they do not exercise this case. With global concurrency one, such a poison occurrence can repeatedly reclaim the only execution lane. This finding follows the installed BullMQ source; I did not run a multiple-crash timing test.
